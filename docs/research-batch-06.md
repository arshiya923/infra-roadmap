# Batch 06 source and correction ledger — in progress

Checked 2026-10-04. Initial two lessons use the [iputils ping manual](https://man7.org/linux/man-pages/man8/ping.8.html), [Linux traceroute manual](https://man7.org/linux/man-pages/man8/traceroute.8.html), [Microsoft ping reference](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/ping), and [Microsoft tracert reference](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/tracert). ICMP references are inherited from the reviewed Batch 05 foundation.

Review decisions:

- Keep count/timeout syntax platform-specific. Windows `/w` is milliseconds; reviewed Linux iputils `-W` is seconds, with `-w` as an overall deadline. Commands specify address family and use numeric loopback only.
- Echo evidence cannot validate application ports, authorization or service-level availability. Missing replies have no RTT observation; they are not zero-millisecond responses.
- Windows tracert's ICMP method is not confused with Linux traceroute's customary UDP default. Linux alternatives are described conceptually and not falsely marked executed when the package is missing.
- A middle asterisk is absent diagnostic evidence, not proof of a failed forwarding hop. Separate source-to-responder RTTs cannot reliably be subtracted into segment delay. Method, return paths, load balancing and response handling constrain interpretation.
- Original synthetic samples are labelled and independent of host observations. The bounded Windows loopback runs verify local tool operation only, not a routed topology.

DNS extension reviewed the [ISC BIND client manuals](https://bind9.readthedocs.io/en/latest/manpages.html), [Microsoft nslookup reference](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/nslookup) and [negative DNS response specification](https://www.rfc-editor.org/rfc/rfc2308.html). The executed BIND clients are version 9.18.39 from Ubuntu 24.04. Direct DNS queries are separated from application resolver behavior. A/AAAA type is separate from IPv4/IPv6 DNS transport. NODATA, NXDOMAIN, SERVFAIL and timeout remain distinct, and process exit is not used as a substitute for expected DNS status/data. TCP is tested explicitly, not as a truncation-fallback claim.

Configuration extension reviewed [Microsoft ipconfig](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/ipconfig), [iproute2 ip](https://man7.org/linux/man-pages/man8/ip.8.html), [address](https://man7.org/linux/man-pages/man8/ip-address.8.html) and [link](https://man7.org/linux/man-pages/man8/ip-link.8.html) manuals. Inspection is separated from mutation; adapter/namespace context is explicit. Configuration presence does not prove delivery, loopback UNKNOWN is not automatically failure, and runtime Linux settings are distinguished from manager-owned persistence. Windows help exit behavior is recorded from execution, not assumed from a generic success convention.

ARP/socket extension reviewed [Microsoft arp](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/arp), [Microsoft netstat](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netstat), [iproute2 neighbour states](https://man7.org/linux/man-pages/man8/ip-neighbour.8.html) and [ss](https://man7.org/linux/man-pages/man8/ss.8.html). Route-selected next hops are separated from remote endpoints, neighbour state from identity, and socket state from application success. Process visibility and namespace boundaries remain explicit. Windows and Linux labels/options are not treated as identical. Queue interpretations remain state-specific; no throughput inference is made from a socket snapshot.

The same owned loopback experiment was executed with Windows netstat and Linux ss. Independent tests checked normal/failure socket cleanup and endpoint scope. The Windows provider selects the exact loopback endpoint and current PID; the Linux provider uses a port filter and verifies the local address. Raw unrelated socket inventory is not saved.

Capture extension checked 2026-10-08: [upstream tcpdump manual mirror](https://man7.org/linux/man-pages/man8/tcpdump.8.html), [TShark manual](https://www.wireshark.org/docs/man-pages/tshark.html), [Wireshark display filters](https://www.wireshark.org/docs/wsug_html_chunked/ChWorkBuildDisplayFilterSection.html) and [capture filters](https://www.wireshark.org/docs/wsug_html_chunked/ChCapCaptureFilterSection.html). The tcpdump.org page was blocked to the browser; the upstream manual mirror supplied the reference. Source review separates capture/display syntax, saved/original lengths, numeric presentation, stream-local indexing and relative/raw sequence presentation. A count limit alone is not an elapsed-time limit; a declared payload length is not evidence that payload bytes were saved.

The new PCAP is generated from scratch without sockets, real host identities or external traffic. TShark and tcpdump independently decode it. Five capture-filter and six display-filter results are asserted against known frame sets; GUI interaction and live capture remain unexecuted at this checkpoint. The optional generator refuses to overwrite different existing content.

Integrated lab reviewed 2026-10-08 against the original requirement to capture ARP, DHCP, DNS, a TCP handshake and ICMP and annotate fields/timings/gateway path. Primary references: DHCPv4 RFC 2131, Dnsmasq upstream manual and BusyBox udhcpc documentation. Real DHCP DORA is matched by transaction and MAC; ACK options are checked separately from route and application evidence. Local DNS remains a control during the missing server return-route fault. A server-side capture proves SYN arrival; recovery requires the original FIELD/OK exchange. Namespace and process ownership is explicit. Live packets are confined to virtual links; GUI and physical path claims remain excluded.
