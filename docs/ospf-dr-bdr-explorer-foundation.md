## Contract and source boundary

`scripts/ospf-dr-bdr-models.js` exports `scenario`, `evaluate`, `html` and `mount`. The preview invokes `html('ospf-dr-bdr')` and `mount('ospf-dr-bdr')`. The evaluator accepts four integer interface priorities 0–255, one to sixteen integer presence masks 0–15, and boolean `ribReady`, `forwardReady`, `returnReady`. Bit zero represents R1; bit three represents R4. Fixed unique router IDs are 1.1.1.1 through 4.4.4.4. Inputs remain unchanged and every call returns fresh result structures.

Each event represents a settled, mutually bidirectional broadcast segment with consistent incumbent declarations. An absent attachment resets its declaration before it rejoins. Priorities remain fixed for the entire supplied history. Healthy eligible incumbents retain their roles; an eligible incumbent BDR promotes when the DR departs, before a remaining eligible router fills the BDR vacancy. Where no incumbent exists, priority ranks candidates and the fixed router ID breaks a tie. This bounded shortcut is reviewed against [RFC 2328 §9.4](https://www.rfc-editor.org/rfc/rfc2328#section-9.4), checked 2026-10-09; it is not a general implementation of the protocol algorithm.

Thirteen cases cover established roles, higher-priority late arrival, R1 attachment reset, R1 rejoining, all participants initially available with no incumbents, equal priorities, all-zero priorities, a single eligible router with four participants, R1 alone, BDR attachment failure, and three independent readiness failures. Changing a browser input replays the selected history from its beginning. It does not predict a live priority change or wait-timer race. The all-participants/no-incumbents case assumes all eligible participants are available for the initial settled election; it does not guarantee that every real simultaneous boot reaches the same discovery set before election.

The six unordered neighbor pairs express expected settled Full/2-Way/Absent relationships, reviewed against [§10.4](https://www.rfc-editor.org/rfc/rfc2328#section-10.4). The network-LSA template expresses the current DR's interface-address link-state ID, advertising router ID, /24 mask and fully synchronized participant RIDs. It is absent when no DR exists or the DR has no Full neighbor, reviewed against [§12.4.2](https://www.rfc-editor.org/rfc/rfc2328#section-12.4.2). These are teaching outputs rather than emitted CLI or retained/flushed LSDB predictions.

R3↔R4 readiness requires both participants, an elected DR and all three supplied readiness declarations. It does not calculate routes, transmit packets, inspect policy or measure a service. The separate [actual runtime](ospf-dr-bdr-runtime-foundation.md) supplies packet and route evidence. Its retained rejected passive-return experiment has old conflicting declarations outside the explorer's scope. The model does not represent partitions, NBMA, point-to-point, timer/neighbor FSM events, flooding, LSA aging, convergence time or continuous packet delivery.
